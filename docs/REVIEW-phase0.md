# 0단계 독립 보안 검토 기록

검토자는 구현 과정을 보지 않은 별도 세션(Opus)이다. 발견 사항은 실제 DB와 핸들러로 재현했다.
결론: 출시된 라우트로 다른 기업 데이터를 읽거나 로그인 없이 읽는 직접 경로는 찾지 못했다. 문제는 안전망 쪽에 있었다.

## 조치한 것

| 등급 | 문제 | 조치 | 회귀 테스트 |
| --- | --- | --- | --- |
| HIGH | 끝난 트랜잭션의 DB 핸들이 살아 있어, 다른 요청(다른 기업)의 문맥에서 쿼리가 실행됨 | 끝난 핸들은 예외를 던지게 함. 깨진 연결은 풀에 되돌리지 않음 | isolation |
| HIGH | 테스트가 DB 서버 전체에 공유되는 `stock_app` 역할의 비밀번호를 저장소에 적힌 값으로 바꿈 | 테스트 전용 역할(`stock_app_test`)과 실행마다 새로 만드는 비밀번호로 변경 | (구성) |
| MEDIUM | 소유자·슈퍼유저로 접속하면 RLS가 조용히 꺼짐 | 접속 역할을 검사해 위험하면 모든 DB 접근을 거부 | isolation |
| MEDIUM | IP 제한이 클라이언트가 보낸 `x-forwarded-for` 를 믿음(우회·사칭 가능) | 설정한 프록시 헤더에서만 IP를 읽음. 형식·길이 검사 | hardening |
| MEDIUM | 로그인 요청이 argon2 계산 내내 DB 연결과 행 잠금을 잡아, 폭주 시 전체가 멈춤 | 조회 → 검증(연결 없이) → 기록의 3단계로 분리. 해시 동시 계산 수 제한 | hardening |
| MEDIUM | 비밀번호 변경의 현재 비밀번호 확인에 잠금·감사 기록이 없음 | 로그인 실패와 똑같이 세고, 한도에서 세션 폐기. 감사 로그 기록 | hardening |
| LOW | 쿼리 오류를 삼킨 트랜잭션이 성공으로 보임 | COMMIT 결과를 확인해 실패로 처리 | isolation |
| LOW | 핸들러가 세션 수준 `set_config` 를 하면 연결에 남음 | 구조 규칙으로 금지 | guard |
| LOW | 자산 이력의 보유자·부서 컬럼에 외래키가 없음 | 복합 외래키 추가 | isolation |
| LOW | 기본 부서 지정을 해제·삭제할 수 있음 | 트리거로 차단 | isolation |
| LOW | 깨진 쿠키 값이 500을 냄 | 쿠키 없음으로 처리 | hardening |
| LOW | 기업 문맥에서 같은 기업 계정의 비밀번호 해시를 읽을 수 있음 | 컬럼 읽기 권한 제거, 시스템 문맥 전용 함수로만 읽음 | isolation |
| LOW | 기업 생성 기록이 그 기업의 감사 로그에 남아 운영자 정보가 노출됨 | 시스템 수준 기록으로 변경 | hardening |
| LOW | 메일 스케줄을 지우면 발송 작업 기록이 함께 지워짐 | 연쇄 삭제 제거, 발송 작업 삭제 권한 제거 | schema |
| LOW | `service_role` 미회수, 시간대 미검증, 쿠키 접두사 없음 | 회수 대상 추가, 시간대 검증, 운영에서 `__Host-` 접두사 | direct-access, hardening |
| 테스트 | 비밀번호 변경 강제가 유형 기반 라우트에서 검증되지 않음 | 테스트 추가 | hardening |
| 테스트 | 문맥 누수 테스트가 기업 문맥 누수를 못 잡음 | 기업·시스템·실패 경우를 따로 확인 | isolation |
| 테스트 | 오류 노출 테스트가 성공 응답만 확인함 | 실제 500 경로로 교체 | hardening |
| 테스트 | 구조 규칙 우회(`export {}`, Server Action, 변수로 넘긴 SQL) | 규칙 강화, 위반 코드를 넣어 실제로 잡히는지 확인 | guard |
| 테스트 | 직접 접근 테스트가 스키마 권한에만 의존 | 스키마 권한을 임시로 연 상태에서도 확인 | direct-access |

## 조치하지 않았거나 일부만 한 것

- **actor_id(작업자) 복합 외래키**: 시스템 관리자(기업 없음)도 기업 안에서 작업하므로 묶을 수 없다. 서버가 항상 세션에서 채운다.
- **IP와 무관한 전역 로그인 제한**: 넣지 않았다. 전역 제한은 공격자가 모든 사용자의 로그인을 막는 수단이 된다.
  IP를 바꿔 가며 하는 시도는 계정 잠금과 해시 동시 계산 제한으로만 막는다.
- **구조 규칙 검사**는 정규식 기반이라 모든 우회를 잡지는 못한다. 사람(또는 검토 세션)의 코드 검토를 대신하지 않는다.
- **메일 스케줄 삭제**: 발송 기록이 있는 스케줄은 DB가 삭제를 거부한다. 삭제 기능은 4단계에서 비활성화 방식으로 만든다.

## 확인하지 못한 것

- 실제 Supabase(Supavisor 트랜잭션 풀링에서의 `set_config` 동작, `service_role` 기본 권한)
- 실제 Vercel·Cloudflare 가 붙이는 헤더
- 위 조치 사항은 테스트로 확인했지만, **조치 이후의 코드를 독립 검토자가 다시 보지는 않았다.** 1단계 검토에 인증 모듈을 다시 포함한다.
