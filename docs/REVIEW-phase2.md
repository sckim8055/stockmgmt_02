# 2단계 검토 기록 (기준 정보와 자산)

범위: 부서 범위·제한 필드 계층(`src/lib/authz/scope.ts`), 자산(`src/lib/assets/*`, `/api/assets/**`),
기준 정보(`src/lib/master/*`, `/api/master/**`, `/api/departments/**`), 화면(`(app)/assets`, `(app)/master`),
그리고 1단계 검토 뒤에 고친 계정·역할·로그인 코드의 재검토.

검토 방법: 코드를 쓰지 않은 독립 검토자(Opus)가 공격 시나리오를 실제 요청으로 재현하고, 변이 테스트 61건을 수행했다.
재현 테스트는 `tests/review2.test.ts` 에 남겼다.

## 결론

- 다른 기업의 행을 읽거나, 바꾸거나, 참조하거나, 존재를 추정하는 경로는 찾지 못했다.
- SQL 주입 경로는 찾지 못했다.
- 기업 **안에서** 권한을 넘는 경로 2건(중간), 상태 전이 규칙의 빈틈 2건, 클라이언트가 500을 낼 수 있는 입력, 테스트되지 않던 보장 여러 건을 찾았고 아래와 같이 조치했다.

## 테스트 보강 (변이 테스트에서 살아남은 항목)

- 라우트별 권한 선언을 표로 고정: `tests/route-permissions.test.ts`. 권한을 다른 것으로 바꾸면 실패한다
  (역할이 여러 권한을 함께 갖고 있어 동작 테스트로는 잡히지 않던 부분).
- 상태 전이 표 전체(상태별 허용 처리 목록), 제한 필드의 조회/수정 권한 분리, 비활성 사용자 지정 필드 값 숨김,
  겹치는 배정의 결정적 재현: `tests/review2.test.ts`.

## 고치지 않고 남긴 것

- **범위 제한 계정에게 "존재 여부·건수"가 보이는 곳**: 다른 부서 자산과 겹치는 시리얼의 409, 직원 퇴사 거부 시 보유 건수,
  모델·카테고리 삭제 거부, 부서 목록(이름), 자산이 범위로 넘어오기 전의 이력. 값은 보이지 않는다.
- 이력 조회 권한이 있으면 "구매가·공급업체가 언제 바뀌었는지"는 보인다(값은 보이지 않는다).
- 자산 처리는 `asset_txn` 에만 남고 `audit_log` 에는 남지 않는다(자산 이력이 그 기록이다).
- `x-expected-company` 는 헤더가 있을 때만 검사한다(화면용 안전장치이지 보안 경계가 아니다).
- 사용자 지정 필드 삭제·제한 변경과 자산 저장이 정확히 겹치는 경우는 직렬화하지 않는다. 정의가 없는 키의 값은 응답에서 빠진다.
- 고유 제약 위반(23505)을 409로 바꾸는 마지막 안전망은 테스트에서 도달하지 않는다(앞단의 잠금이 먼저 막는다).
- 요청 본문 크기 상한은 확인하지 못했다(Next.js 기본 동작에 의존).

## 검토가 필요한 보호 파일 관련 사항

- `src/lib/http/route.ts`: 이 단계에서 고유 제약 위반(23505) → 409 변환을 추가했다. 독립 검토 범위에 포함되어 검토받았다.
- `tests/guard.test.ts`: 정규식이 잡지 못하는 형태가 있다 — `.query(SQL_MAP[key])`(현재는 `Object.hasOwn` 으로 안전),
  `.query([...].join(''))`, `db['query'](...)`, `const SQL_X = 'a' + 변수`. 가드를 강화하려면 이 파일을 고쳐야 한다. **미조치.**
- `src/lib/db/pool.ts` `assertSafeRole`: `app` 스키마·함수의 소유 여부는 검사하지 않고, 결과를 프로세스 수명 동안 캐시한다. **미조치.**

## 확인하지 못한 것

- 실제 Supabase·프록시 뒤에서의 동작.
- 화면 브라우저 테스트는 작업자가 임시 DB로 수행했고(기준 정보 39항목, 자산 57항목 통과 보고), 저장소에 자동화되어 있지 않다.
  수정 이후의 화면은 브라우저로 다시 확인하지 않았다.
- 이 문서의 조치 내용 자체는 독립 검토를 다시 받지 않았다(다음 단계 검토 범위에 포함한다).
