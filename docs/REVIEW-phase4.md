# 4단계 검토 기록 (한계 수량, 알림, 메일 일정)

범위: 한계 수량·알림(`src/lib/alerts`, `/api/thresholds`, `/api/alerts`), 메일 일정(`src/lib/mail`, `/api/mail/**`),
마이그레이션 0007, 재고 처리에 넣은 판정 호출, 화면, 그리고 3단계 검토 뒤에 고친 코드(특히 새로 쓴 엑셀 읽기)의 재검토.

검토 방법: 코드를 쓰지 않은 독립 검토자(Opus)가 공격 입력과 동시 요청을 실제로 만들어 측정하고, 변이 테스트 69건을 수행했다.
재현 테스트는 `tests/review4.test.ts` 에 있고 조치 뒤 모두 통과한다.

**이 단계에 없는 것**: 실제 메일 발송과 정기 실행기. 일정 관리와 미리보기까지만 있다.

## 결론

- 다른 기업의 데이터를 읽는 경로, SQL 주입 경로는 찾지 못했다. 알림을 받는 사람의 선정, 부서 범위, HTML 이스케이프는 견뎠다.
- **심각한 문제는 다시 가용성이었다.** 알림함 조회만으로, 또는 엑셀 업로드 한 건으로 다른 기업의 요청까지 실패시킬 수 있었고,
  재고 처리끼리 교착에 빠졌다. 모두 이 단계에서 내가 넣은 코드(요청 안에서 계산하는 날짜 알림, 행마다 하는 한계 수량 판정)가 원인이다.

## 테스트 보강 (변이 테스트에서 살아남은 항목)

카테고리 한계 수량, 자산 배정·반납·부서 변경과 주변기기 반납에서의 판정, 부서 한계 수량의 집계 범위, 꺼진 역할의 수신 제외,
퇴역 자산·반납된 대여의 알림 제외, 비활성 수신 계정, 받는 사람 50명 합산 상한, 부서 메일의 주변기기 대여 범위,
조정 상한, zip 목록 검사(중복 이름·항목 수·암호화), 글자 목록 한도.

## 고치지 않고 남긴 것

- **날짜 기준 알림은 그날 누군가 알림함(또는 메뉴의 읽지 않은 수)을 불러올 때 계산된다.** 조회 요청이 쓰기를 한다(하루 한 번).
  정기 실행기가 생기면 그쪽으로 옮긴다.
- 그 계산을 떠맡은 요청은 받는 사람이 많은 기업에서 1~2초 걸릴 수 있다.
- 나중에 알림함 권한을 얻은 사람은 이미 알려진 건을 받지 못한다.
- **한계 수량을 만들거나 다시 켜는 순간과 겹친 재고 변동은 판정을 한 번 놓칠 수 있다**(재현하지 못한 추정). 그 모델의 다음 변동에서 바로잡힌다.
- **엑셀 파일을 읽는 동안 프로세스가 멈추는 시간은 최악 약 0.6초다**(3단계 기록의 0.3초는 부분 하나만 잰 값이었다).
- **2,000행 자산 업로드가 자산 2만 대인 기업에서 38초 걸렸다**(자산이 적으면 약 10초). 원인을 조사하지 않았다.
- 사용자 지정 역할에서는 `mail.schedule:read` 만으로 미리보기의 보유자 이름·수량을, `alert.inbox:read` 만으로 알림의 자산 태그·보유자 이름을 본다.
  기본 역할 구성에서는 문제가 없다.
- 월간 일정의 29~31일은 그 날짜가 없는 달을 건너뛴다. 주기를 주간에서 월간으로 바꾸면 요일 숫자가 날짜로 읽힌다(화면은 함께 바꿔 보낸다).
- 부서 범위를 좁혀도 이미 받은 알림은 지워지지 않는다.
- 기업 단위 잠금 열쇠는 32비트 해시라 드물게 다른 기업과 겹칠 수 있다(불필요한 409 한 번).
- 이전 단계에서 남긴 항목은 그대로다.

## 검토가 필요한 보호 파일 관련 사항 (미조치)

- 테이블을 추가하려면 테이블 수를 세는 보호 테스트(`tests/direct-access.test.ts` 등)를 고쳐야 한다. 그래서 이 단계는 테이블 없이 인덱스만 추가했다.
- 정기 실행기에는 `withSystem` 허용 목록 변경이 필요하다.
- 이전 기록의 `guard.test.ts` 강화, `assertSafeRole`, `pool.on('error')` 도 그대로다.

## 확인하지 못한 것

- 실제 프록시 뒤에서 느린 업로드가 어떻게 끊기는지, Supabase, 여러 프로세스 배포.
- 화면 브라우저 테스트는 작업자가 임시 DB로 수행했다(77항목 통과 보고, 스크립트 `/tmp/ui-smoke-alerts/`). 이번 수정 뒤에는 다시 돌리지 않았다.
- 이 문서의 조치 자체는 독립 검토를 다시 받지 않았다. 다음 단계 검토 범위에 포함한다.
