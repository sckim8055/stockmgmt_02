# 아키텍처 (0단계 기준)

## 요청 처리 순서

```
브라우저 ──▶ Next.js 서버 (route()) ──▶ PostgreSQL (app 스키마, stock_app 역할, RLS)
             0. 로그인: 기업코드 + 로그인 ID + 비밀번호
             1. 출처 검사(CSRF) → 세션 확인
             2. 계정·기업 활성 여부, 비밀번호 변경 강제 여부
             3. 권한 판정 (사용자 유형 → 역할의 허용 목록)
             4. tenant(): 트랜잭션에 app.company_id 를 설정하고 쿼리
             5. (2단계부터) 부서 범위·제한 필드 적용
             6. 감사 로그
```

브라우저는 DB에 직접 접속하지 않는다. Supabase에 올리더라도 로그인·데이터 API는 쓰지 않고 Postgres로만 쓴다.

## 기업 격리는 2중이다

| 층 | 방법 | 막는 것 |
| --- | --- | --- |
| 서버 | `tenant()` 가 세션의 기업 ID로만 트랜잭션을 연다 | 요청 조작(다른 기업 ID를 보내는 것) |
| DB | `stock_app` 역할 + RLS `company_id = app.ctx_company_id()` | 서버 코드가 기업 조건을 빠뜨린 경우 |
| DB | `(id, company_id)` 복합 외래키 | 다른 기업의 모델·부서·직원을 참조하는 행 |

RLS는 서버 코드의 실수를 막는 안전망이다. 서버 자체가 탈취되면 `app.system=on` 을 설정할 수 있으므로 그 경우까지 막지는 못한다.
부서 범위는 RLS로 강제하지 않고 서버에서만 적용한다(2단계). 그래서 범위 테스트가 필수다.

## DB 역할

| 역할 | 용도 | 접속 주소 |
| --- | --- | --- |
| 소유자(예: postgres) | 마이그레이션 전용 | `MIGRATION_DATABASE_URL` — 앱 서버 환경에는 넣지 않는다 |
| `stock_app` | 앱 서버 | `DATABASE_URL` |

`stock_app` 은 소유자가 아니라서 RLS를 우회할 수 없고, 이력·감사 테이블에는 UPDATE/DELETE 권한이 없다.

- 서버는 시작할 때 접속 역할을 검사한다. 슈퍼유저, BYPASSRLS, 테이블 소유자로 접속하면 모든 DB 접근을 거부한다
  (`DATABASE_URL` 에 소유자 계정을 잘못 넣으면 RLS가 조용히 꺼지기 때문이다).
- `app_user.password_hash` 는 앱 역할이 읽을 수 없다. 인증 처리(시스템 문맥)에서만 `app.auth_password_hash()` 로 읽는다.
- 트랜잭션이 끝난 DB 핸들은 다시 쓸 수 없다. 연결이 풀로 돌아가 다른 기업의 문맥으로 재사용되기 때문이다.
- 역할은 DB 서버 전체에 공유된다. 테스트는 `stock_app_test` 라는 별도 역할과 매번 새로 만든 비밀번호를 쓴다.
  같은 서버에 개발 DB와 운영 DB를 함께 두면 `stock_app` 비밀번호도 공유되므로, 운영 DB는 별도 서버에 둔다.

## 인증

- 비밀번호: argon2id 해시만 저장. 규칙은 10자 이상, 문자 종류 3가지 이상, 로그인 ID 포함 금지.
- 세션: 무작위 32바이트 토큰을 HttpOnly·SameSite=Lax 쿠키로. DB에는 SHA-256 해시만 저장.
  최대 12시간, 미사용 2시간이면 만료. 비밀번호 변경·비활성화 시 즉시 무효.
- 잠금: 5회 연속 실패 시 15분. 비밀번호 변경 화면에서 현재 비밀번호를 틀리는 것도 똑같이 센다.
- IP 제한: 같은 IP에서 15분에 30회 실패하면 그 IP의 시도를 거부. IP는 `TRUSTED_IP_HEADER` 로 지정한
  프록시 헤더에서만 읽는다. 지정하지 않으면 IP 제한은 동작하지 않는다.
- 부하 제한: 비밀번호 검증은 DB 연결을 잡지 않은 채로 하고, 동시에 계산하는 수를 제한한다(`HASH_CONCURRENCY`).
  대기열이 넘치면 "잠시 후 다시"로 거절한다.
- 임시 비밀번호: 서버가 만들어 한 번만 보여준다. 72시간 유효, 첫 로그인 때 변경 강제.
- 로그인 실패 응답은 원인(기업코드·ID·비밀번호·잠금)을 구분하지 않는다.

### 알려진 한계

- 계정 잠금은 남이 일부러 틀려서 특정 계정을 15분간 잠글 수 있다는 뜻이기도 하다.
- IP 기준 제한은 `TRUSTED_IP_HEADER` 를 설정해야 동작하고, 그 헤더를 프록시가 덮어쓴다는 전제에서만 안전하다.
  서버를 프록시 없이 직접 노출하면 그 헤더도 위조할 수 있다. IP를 바꿔 가며 하는 시도는 계정 잠금으로만 막힌다.
- 해시 동시 계산 제한은 프로세스 단위다. 로그인 폭주 시 정상 사용자의 로그인도 "잠시 후 다시"를 받을 수 있다
  (이미 로그인한 사용자의 요청은 영향받지 않는다).
- 감사 로그의 actor_id 는 복합 외래키로 묶지 않았다(시스템 관리자도 기업 안에서 작업하기 때문). 서버가 항상 세션에서 채운다.
- 임시 비밀번호를 발급한 관리자는 사용자가 바꾸기 전까지 그 계정으로 로그인할 수 있다(감사 로그로 추적).
- 2단계 인증과 SSO는 없다.

## 0단계에 없는 것
