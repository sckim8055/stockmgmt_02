# 3단계 검토 기록 (주변기기와 엑셀 업로드)

범위: 주변기기(`src/lib/peripherals`, `/api/peripherals/**`), 엑셀 업로드(`src/lib/import`, `/api/import/**`), 마이그레이션 0006,
새 의존성 fflate, 화면(`(app)/peripherals`, `(app)/import`), 그리고 2단계 검토 뒤에 고친 코드의 재검토.

검토 방법: 코드를 쓰지 않은 독립 검토자(Opus)가 공격 입력을 실제로 만들어 시간을 재고, 변이 테스트 55건을 수행했다.
재현 테스트는 `tests/review3.test.ts` 에 있고 조치 뒤 모두 통과한다.

## 결론

- 다른 기업의 데이터를 읽거나 바꾸거나 존재를 알아내는 경로, SQL 주입 경로는 찾지 못했다.
- 주변기기 수량은 500건의 동시 혼합 처리 뒤에도 재고·대여·이력이 일치했다.
- **심각한 문제는 가용성이었다.** 재고 담당 권한만 있는 계정 하나가 작은 엑셀 파일 하나, 또는 동시 업로드 5건으로
  모든 기업의 서비스를 멈출 수 있었다. 아래와 같이 고쳤다.

## 고치지 않고 남긴 것

- **2,000행 자산 업로드는 약 10초 걸리고, 그동안 그 기업의 계정·역할·부서·기준 정보 변경이 기다린다.** 다른 기업과 일반 조회·자산 처리는 영향이 없다. 줄이려면 행 단위 쿼리를 묶어야 한다.
- **엑셀 파일을 푸는 동안(최대 약 0.3초) 그 프로세스의 다른 요청이 멈춘다.** 별도 스레드로 옮기지 않았다(동시 1건 제한과 한도로 상한을 둠).
- 프로세스가 여러 개인 배포(서버리스 등)에서는 "한 번에 하나" 제한이 프로세스마다 따로 적용된다. 기업 단위 잠금은 DB 에 있어 그대로 유효하다.
- 업로드 도중 쿼리 오류가 나는 경우의 동작(전체 실패, 500)은 테스트하지 못했다. 사용자 지정 필드 키 100개 상한도 테스트가 없다.
- **수식 주입**: `=`, `+`, `-`, `@` 로 시작하는 값이 그대로 저장된다. 아직 내보내기 기능이 없어 영향은 없다. 내보내기를 만들 때 반드시 처리한다.
- 0으로 시작하는 사번을 숫자 셀로 넣으면 앞의 0이 사라진다(엑셀이 저장할 때 이미 사라진다). 양식 안내에 적었다.
- 마이그레이션 0006 은 이력 테이블을 다시 쓴다(배포 중 잠금). 지금은 자료가 없어 문제가 없다.
- 2단계에서 남긴 항목(범위 제한 계정에게 보이는 존재 여부·건수 등)은 그대로다.

## 검토가 필요한 보호 파일 관련 사항 (미조치)

- `src/lib/db/pool.ts`: 대기 중인 연결이 끊길 때의 오류 처리(`pool.on('error')`)가 없어 서버 로그에 처리되지 않은 예외가 찍힌다.
- 2단계 기록의 `tests/guard.test.ts` 강화, `assertSafeRole` 보강도 그대로 남아 있다.

## 확인하지 못한 것

- 실제 프록시·Supabase 뒤에서의 동작(요청 크기 제한 포함).
- 화면 브라우저 테스트는 작업자가 임시 DB로 수행했다(33항목 통과 보고). 저장소에 자동화되어 있지 않고, 이번 수정(429/409/403 응답 추가) 뒤에는 다시 돌리지 않았다.
- 이 문서의 조치 자체(특히 새로 쓴 엑셀 읽기)는 독립 검토를 다시 받지 않았다. 다음 단계 검토 범위에 포함한다.
